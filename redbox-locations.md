## What can appear

## What changes it

| Trigger | State change and effect |
| --- | --- |
| Open / switch project / retry | `useLocation` scopes reads to user, session generation, project and service, subscribes to the location document and loads it on entry. It attempts `createInitial` once per scope for a missing list, then refetches. Dashboard portal subscriptions read the projection independently. Pull to refresh loads both. A portal action refreshes the projection and then runs the Locations refresh callback, which also refreshes the projection. |
| Client adds, edits, removes or saves a draft | Portal local changes start a debounced, serialised per-section save. `savePortalDraft` verifies session and selected live step, date/owner entitlement and client ownership, then normalises venue values, merges existing non-client rows, applies both quotas and writes items/metadata. `multipleLocations` is accepted only when plan policy allows multiple. Projection usually stays client-owned. Browser saving/saved/error does not render in the mobile box. |
| Client submits | Section submit validates payload and requiredness, merges protected fields, writes `status: locked`, `actionOn: photographer`, `clientSubmittedAt` and update metadata. The projected review arrives asynchronously. Firebase sends the photographer push or email on a fresh submission timestamp, not merely on a take-over. |
| Client skips or confirms feedback | Locations is required by default; the skip endpoint checks step optionality, including explicit legacy/alternate setup overrides. An accepted skip sets `status: finalized`, `skippedByClient/skipped: true`, `finalized: true`, `actionOn: none` and `skippedAt`. The eligible client feedback confirmation clears revision metadata, stamps `clientReviewConfirmedAt` and leaves `unlocked/client`; the box has no feedback-acknowledged variation. |
| Photographer takes over / hands back | `claimPortalSection` verifies membership/permission and unlocked status; it keeps items, writes `locked/photographer` and clears revision metadata. Revision callable requires selected, pre-event, nonfinalised `locked/photographer` plus a nonempty sanitised note of up to 1,000 characters. It writes `unlocked/client`, `finalized: false`, revision fields and update timestamp. Shared buttons disable while pending. Confirmations close on success; failures leave them open. Hand-back and takeover do not invoke the shared hook's local error handler, so verify error feedback from the lower layer before relying on it. |
| Photographer taps Finalise locations | This screen does **not** opt in to the shared generic finalise action. `LocationService` deduplicates in flight per project and geocodes sequentially for missing pins, preserving usable coordinates, refreshing/clearing generated notes and keeping private notes within their field limit. The online `geocodeProjectLocation` callable checks owner, entitlement, date and portal ownership and uses the paced OpenCage repository. The service saves pins, notes and `finalized/status/actionOn` together via `document.replace`. All successes yield `true/finalized/none`. A failed venue can still save resolved pins and diagnostics but leaves the list editable, then shows “Could not finalise …” and refetches. Provider/config, quota or throttle, no match, connectivity, bad payload, permission or conflict can stop progress. There is no per-item progress or pending Finalise label in this card. |
| Generic Firebase finalisation / last selected section finalises | The separate `finalizePortalSection` requires a reviewable locked photographer step, stamps `approvedAt/approvedBy`, clears revision flags and writes `finalized/none` without geocoding. Location-screen finalisation calls the geocoding path described above. A document finalised trigger requests projection rebuild. When every selected section is finalised, it sets access to finalised/disabled and removes the access token hash. |
| Photographer taps Unlock Locations | Upcoming shared section calls `claimPortalSection(..., true)`, permitted even with a closed link when otherwise eligible. It clears `finalized`, writes `locked/photographer` and does not revive the link. An unshared list uses `config.patch` with `finalized: false, status: unlocked`; it does not explicitly reset `actionOn`. Shared unlock has local pending and app error handling. Server and UI reject shared reopen on/after wedding day. |
| Offline / reconnect / refresh conflict | Location add/edit/delete and config patches go through `executeOrEnqueueWrite`. Entitled accounts persist before returning optimistic success and overlay queued items/config at read/subscription. Other accounts need connectivity. Geocoding/finalisation and portal claim/revision require online calls. Replay can fail on entitlement, ended project, new ownership/finalisation, quota, or changed item/config base. Pending and failed state is surfaced by the global offline queue, not in the local action card. Initial creation and online finalisation use timestamp-checked document replacement. Direct-call rejection maps quota to capacity and other non-applied outcomes to a generic permission error. |

## Findings and smallest fixes

1. **Finalise is offered during the live client turn.** The presenter checks only the event day, while the callback checks only existing finalisation. The server rejects client-owned geocoding and the final document replacement. Derive `canFinalize` from the existing ownership and date predicates in the location composition hook and use it for visibility and dispatch. Reuse the geocoding action. [Presentation](C:/eye-doo-monorepo/apps/mobile/src/components/features/locations/locations-presenters.tsx:55) · [Composition](C:/eye-doo-monorepo/apps/mobile/src/hooks/dashboard/home/use-dashboard-locations.ts:232) · [Policy](C:/eye-doo-monorepo/apps/functions/mobileMutationPolicy.ts:74)
2. **Finalisation can overwrite a concurrent venue change.** Source-derived race: the service geocodes the first snapshot, then the repository re-reads and uses the newer `config.updatedAt` as its precondition while writing the first snapshot’s items. A concurrent authorised edit that lands before that second read can pass comparison. Carry the original source version through the existing call and test a deferred geocode with an intervening write. [Service read](C:/eye-doo-monorepo/apps/mobile/src/services/location-service.ts:426) · [Repository reread](C:/eye-doo-monorepo/apps/mobile/src/repositories/firestore/firestore-location-repository.ts:412) · [Server comparison](C:/eye-doo-monorepo/apps/functions/mobileMutationCallables.ts:78)
3. **The same wording describes submitted work, takeover and reopen.** The projection calls all of those photographer review, and legacy submission timestamps can survive reopen. Conversely, a closed or unshared finalised list can display advice to add/edit above the locked card. Use a single localised sentence, with real finalisation and event locks taking precedence over editable wording. Use neutral **Ready for your review** unless a current submission is evidenced. Show the same eligible primary **Finalise locations** or **Unlock locations** under it, with hand-back below. Preserve unlock for an eligible empty finalised list. [Guidance](C:/eye-doo-monorepo/apps/mobile/src/utils/presentation/portal-step-status-card.ts:72) · [Claim config](C:/eye-doo-monorepo/apps/functions/portal/section/sectionCallables.ts:330)
4. **Pins can remain attached to an old address.** The portal draft/submit merge preserves an existing `geopoint` even when a client-owned venue address changes; mobile finalisation skips any valid-looking pin. Fix the address/pin invalidation in the existing normalisation path if verified with the save/submit fixtures. Generic approval can also mark venues finalised with no pins. Keep the mobile Locations CTA on its geocoding handler and test hand-back, client address change, submit and re-finalise. [Portal merge](C:/eye-doo-monorepo/packages/domain/src/portal/draft/sectionDraftValidation.ts:98) · [Geopoint short-circuit](C:/eye-doo-monorepo/apps/mobile/src/services/location-service.ts:435)
5. **Stale quota and ambiguous plan/access states.** The UI counts zero items during non-success even with cached rows visible, and treats a catalogue error as plan lock. A failed portal read without cached data can leave the hook treating the list as unshared. A current valid link may disagree with projected expiry or step/status. Reuse cached/overlay list length for the cap. Verify missing plan versus failed lookup, and avoid promising a local unshared unlock while sharing remains unresolved. Use policy outcomes for meaningful errors.
