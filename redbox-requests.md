## What can appear in the box

The route uses a scrollable `DashboardShell` with four list skeletons for first load. Supported content uses one `StandardAppStack space="sectionContent"`, containing a centred `StandardAppText role="editorialBody"`, the eligible workflow buttons, and then list content. ### List contents in the same area

| Condition | Rendering and source |
| --- | --- |
| Nonempty parsed list, all accessible phases | Three subtle, small, equal-fill badges in a wrapping `StandardAppInline`: **Pending: n** (warning), **Approved: n** (success), **Not feasible: n** (error). Counts come from current `items[]` and exact `requested / approved / notFeasible` values. All author sources count, including rows marked disabled. Zero counts remain visible. Badges are summaries with no filter action. Service also derives total, resolved and image counts, which the box does not show. |
| Initial error and no usable list | Shell-owned error and retry. Pull-to-refresh uses the same handler to refresh the list, then the dashboard portal. |
| Later error with stale list | Compact, plain `StandardAppStatusState` before the badges or empty card: **Couldn’t refresh this list** and “Showing the last loaded requested shots. Pull down to retry.” **Retry** refreshes both. Any status badges continue to describe the stale list. |
| Empty list after load | Raised-card empty state with camera icon, **No Requested Shots Yet** and “Add the shots you or your client want to remember.” No badges. **Add request** appears inside the card only if the add gate is open. |
| Nonempty and add eligible | **Add photo request** floating action outside the red box, related because eligibility changes while ownership changes. It is absent in the empty state. At the photographer cap the route can show “You've added {{count}} requests, the most you can add. Requests from your client don't count towards this.” below the rows. That message is independent of the reason Add was suppressed. |

The row summary below the red box can contain title, priority (**Must have**, **Nice to have**, **If possible**), attribution, result badge, description, optional **View reference** image and viewer, optional **Photographer notes**, and review actions. These row results directly drive the header badges. The footer review actions appear only when raw list status is `locked`, raw `actionOn` is `photographer`, raw `finalized` is false, the row status is `requested`, and the row is not tagged as photographer-created. An unknown legacy author can therefore be reviewable. ## Actions and transitions

| Trigger | Effects on data and rendering |
| --- | --- |
| Client creates or edits a draft, adds/removes a request, or attaches a reference | Portal editor changes client-owned rows and keeps photographer rows read-only. Draft callable transaction validates session, access, section, entitlement, ownership, IDs and limits. It merges rows with the server snapshot, preserves existing outcomes and photographer notes, defaults new client rows to `requested`, and writes items and metadata without changing the phase. A client-owned row omitted from the draft can be removed. Photographer-owned rows must remain identical. A concurrent conflicting photographer row makes the draft fail validation. |
| Client submits | Portal transaction reapplies the typed merge and quotas, writes current rows, `locked/photographer`, `clientSubmittedAt` and `config.updatedAt`, and clears revision/client confirmation markers and legacy lock. List and projection updates reach mobile independently. The submission trigger deduplicates by the new submission timestamp and sends an Expo push or email fallback. Projection triggers queue the phase rebuild. |
| Client skips or confirms review | Optional skip persists finalised/none plus skip markers and time, keeping row results. It can bypass photographer resolution because it is a separate transition. Guarded confirm-review accepts the client-review state, writes unlocked/client and confirmation time, and clears revision markers. Neither is mobile row approval. Marking the last selected step finalised can also set portal access to finalised and disable the link. |
| Photographer taps **Take over this section** | Opens **Take Over This Section** with “Your client will no longer be able to edit this section in the portal. Anything they have added stays.” Confirm **Take over** or **Cancel**. `claimPortalSection` validates owner/plan and selected configured step, requires canonical unlocked for claim, then writes locked/photographer, retaining request outcomes and not creating a new client submission. |
| Photographer taps **Hand back to client** | Opens **Hand Back to Client**, with “Your client can edit this section in the portal again. They will see this note.” Editable **Note to your client** defaults to “Handed back to you to complete”; blank trimmed note is a no-op. **Hand back** uses `requestPortalSectionRevision` to validate pre-wedding owner/step/locked-photographer state and write unlocked/client, revision fields, false finalised and server timestamp. **Cancel** dismisses. Prior row outcomes remain. |
| Photographer taps **Finalise section** | Direct action without an extra confirmation. The existing hook requires live projected photographer review, local non-finalised, loaded list and every row resolved. Repository tries to flush the section queue, then calls `finalizePortalSection`. Server uses pre-wedding canonical locked+stored photographer, selection and authorization; it writes finalised/none, boolean finalised, `approvedAt / By`, and deletes revision/legacy lock fields. It does not inspect individual outcomes. No Requests reopen action or callable support. |
| Photographer adds a request | **Add Photo Request** uses a `UnifiedFormModal` for required **Title**, **Description**, and **Priority**. **Save Request** trims title and description, sets both description representations and false capture checkbox. Service creates a generated ID, `createdBy/updatedBy: photographer`, and **approved** immediately, which increments Approved without client input. The form has no reference upload control. |
| Photographer reviews a pending row | **Approve** or **Not feasible** opens **Review {{itemName}}**. The modal allows either result and optional notes. **Save response** trims notes, service rejects absent/previously reviewed item or frozen/wrong-locked owner state, then stores status, notes and `updatedAt / updatedBy`. Success closes, refetches list and refreshes portal. Failure leaves the modal open with error handling. Save spins and blocks dismissal. Dirty dismissal allows discard or keep editing. |

### Images, pending, and conflicts

- Portal uploads are online. They validate permitted type, file size/content, writable link and step, client ownership, image entitlement, project/item identity and quota, and use signed Storage upload/validation. The web editor can show uploading, validating, complete or failed before the committed list contains the URL. The mobile badge totals do not count images. If the saved URL arrives in the list, the request row gains an image and viewer. Upload is blocked while the photographer has the turn, including after submit. Portal upload guard permits replacing an existing image at cap because it is no growth, while the web editor’s global `canUploadPhotoRequestImages` can suppress that action at cap. ## Findings and smallest fixes

1. **Align the quota contract before relying on the cap copy.** The mobile Add gate counts only exact photographer-owned rows. The portal editor and draft/submit first count non-photographer rows against the portal limit. Mobile mutation quota and the extra shared mobile quota check in portal draft/submit count all rows against `photoRequests.maxPerProject`. For example, two Basic client requests can leave mobile Add visible at 0/2 photographer rows, yet a third total row can fail with `quota_items`. Confirm whether the product intends separate quotas or a combined cap, then align the three checks and copy. The footer currently also compares raw `>= limit`, which can yield a misleading message for an unlimited sentinel or when ownership/date was the true blocker. [Mobile add gate](C:/eye-doo-monorepo/apps/mobile/src/hooks/list-hooks.ts:438) · [Shared count](C:/eye-doo-monorepo/packages/domain/src/quota/mobile-list-quota.ts:126) · [Draft quota](C:/eye-doo-monorepo/apps/functions/portal/section/draftCallables.ts:102)
2. **Use the current list and portal state together for availability.** Review buttons can survive on a stale locked/photographer list after the event, under the read-only intro. The row service also accepts a broader range than the screen by only rejecting finalised or raw locked under someone else. Use the existing event phase and canonical lock/owner inputs for display and action eligibility. Avoid promising editable access on a finalised closed/unshared list, and treat takeover and reopen as photographer ownership rather than evidence of a new client submission. The existing **Ready for your review** wording fits both. [Row gate](<C:/eye-doo-monorepo/apps/mobile/src/app/(protected)/(app)/(dashboard)/(lists)/requested.tsx:200>) · [Review service](C:/eye-doo-monorepo/apps/mobile/src/services/photo-request-list-service.ts:377)
3. **Make the finalise rule deliberate.** The local condition permits an existing empty list and suppresses finalise for any pending row, including a legacy photographer-created pending row the screen cannot resolve. The callable checks section context but does not require all rows resolved, so stale or concurrent data can bypass the local rule. If resolution is required, enforce it transactionally for Requests and decide whether empty lists qualify. A related decision is whether a material change to a previously reviewed client request after hand-back should reset its result. Today the merge preserves that status and notes, so a changed description/attachment can stay Approved and non-reviewable. Match choice and spacing with the other sections using existing variants. Distinguish row **Approved** from the finalised section in the copy. Keep the three counts and zero values.
