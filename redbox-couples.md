# Couple Shots workflow header audit

The highlighted area combines client workflow, list-management controls and a progress count whose meaning changes with the wedding phase. At the audited commit the screenshot state also has a **Waiting for client choices** heading. **Client selection 2** is the second workflow stage. **Choose for client** claims ownership, then presents a read-only selection checklist. Fix the action promise and the ownership gates before tightening the layout.

Source baseline is `stabilize` at `9ac94ac18630919f9709c010639c3b469c3f12e7`. This report covers the area above the first category and the actions that affect it. ## What renders and when

The Couple Shots route passes its own step ID, feature checks and heart icon into `DashboardShotListScreen`. The active Couple Shots list auto-fetches and subscribes independently from Group Shots. The date comes from the active project and is compared in the account timezone using the mounted calendar clock. A missing date resolves to upcoming here. The portal step is picked by ID even if the link is inactive. The phase checks completed event first, then client-selection entitlement, then wedding-day state, approval/review, and lastly offering readiness. ## What to change first

1. **Represent the selection action truthfully.** Keep **Take over this section** only if taking ownership for review is the product behavior. If photographers must choose, add an explicit permitted selection-edit affordance that writes `clientSelected` in the photographer-owned review state through the existing item patch path. Today the row handler can write `isDisabled` or `isChecked`, and review disables its selection checkbox. Clarify confirmation wording, especially for zero choices, skipped steps and takeover with an old submitted timestamp. Keep capture independent of approval.
2. **Use actual client access and align callable prerequisites.** The awaiting phase and takeover use the presence and status of the projected step without checking that its link is active, while structural edit uses live access. The offer CTA checks enabled/included/prepared but omits access status. Stale projection can advertise review approval which the server rejects. Use the existing live-step and ownership helpers in the orchestration/read layer to decide the available action and copy, without changing the meaning of persisted selection or inventing a second workflow model. Existing server legacy mismatches around `review`, `locked` and owner require tests. Avoid promising an active client after disable, expiry, entitlement loss, step removal or day change.
3. **Resolve wedding-day mismatches before advertising a checklist.** Missing portal step copy says “Only checked shots are shown” while the mapper shows all offers. The unresolved path offers capture checks but the authoritative write policy rejects them. Decide whether to allow capture on offered rows in this phase or make it visibly read-only. Confirm whether photographer-claimed or skipped lists should use selected-only wedding-day behavior, including empty results. Use eligible displayed rows for the empty state where filtering intentionally excludes every shot.
4. **Simplify hierarchy using the existing slots.** Put a short status sentence above the available action and keep numeric data below. Stage numbers are redundant with phase copy and the screenshot's **Client selection 2** reads like a count. Choose whether the formal total belongs in the header. If retained, explicitly make room for both the total and progress using existing components and verify text scaling, because currently progress masks it. Align checked/taken nomenclature across labels, category subtitles and accessibility. The computed unresolved `guidance.warning` is presently unused in screen rendering. The English dictionary supplies current wording, and legacy stored unsupported language preferences coerce to English. [Locale](C:/eye-doo-monorepo/apps/mobile/src/i18n/resolve-locale.ts:12)
5. **Verify status and persistence end to end.** Extend existing shot workflow, header/surface and Functions policy tests for portal absent/unshared/enabled/closed/expired, stale list vs projection, Basic without client selection, Free lapse, each day phase, skipped or zero selections, post-claim selector behavior, timing row/header precedence, queued approval and rejected replay. Check TalkBack reads what the count represents and 200% text fits. Update active architecture/testing, design and button audits and the stale Maestro checkpoint `shot-lists-phase-guidance` to the real `couple-shot-list-intro`. Existing tests cover timing visibility on review rows but do not prove the total chip renders alongside progress.
