### Actions and pending feedback

| Action | Trigger, write and feedback |
| --- | --- |
| **Take over this section** | Opens **Take Over This Section**. The confirmation says the client loses edit access and existing input stays; **Take over** or **Cancel**. Calls `claimPortalSection` with Timeline and no reopen flag. It disables the header button while pending and only closes on success, then refreshes projection and list. |
| **Hand back to client** | Opens **Hand Back to Client** with “Your client can edit this section in the portal again. They will see this note.” Multiline **Note to your client** defaults to “Handed back to you to complete.” **Hand back** sends a trimmed nonblank note through the revision callable. **Cancel** and the close affordance dismiss. Only closes after success. The shared portal dialogs do not show the same explicit confirmation spinner as Timeline summary dialogs. |
| **Use template** | In overflow with unlocked timeline and valid event date; also in the empty state. **Choose a timeline template** offers **Classic UK wedding day**. The generated list is sliced to a finite plan limit. A populated list requires **Replace existing events?** and **Replace events**. Applying persists a full document replacement; the picker/confirmation tracks applying and stays open on failed result. Success toast **Timeline template applied.** A missing date is rejected. |
| **Finalise timeline** | Menu when nonempty and unlocked; code also explicitly allows a local review-locked timeline, including after the event where the screen handler immediately returns false. **Finalise timeline?** explains edit lock and later unlocking. **Finalise** calls Firebase portal finalisation if the step is live, otherwise a mobile config patch with `finalized:true,status:finalized,actionOn:none`. On the live path, Functions now requires an upcoming, selected, photographer-owned `locked` step. |
| **Unlock timeline** | Menu if raw finalised or raw `status=locked` and event not complete. **Unlock timeline?** promises edits, reordering and event changes. **Unlock** applies a mobile config patch `{finalized:false,status:unlocked}`, leaving stored `actionOn` untouched. It does not use portal `claimPortalSection` with `reopenFinalized`. |
| **Clear all events** | Destructive overflow confirmation when nonempty and unlocked; removes all event rows and resets counters using the existing timeline service, without handing back or claiming any portal step. |
| Summary confirmations | **Cancel** and X, blocked during submission. Confirm button spins, and a failed response keeps the dialog open. Finalise, Unlock and Clear have specific success and generic retry toasts. A live finalise success refreshes list and projection. The preview progress track persists nothing. |

## Data, entitlement and transitions

| Data | Contract and effect |
| --- | --- |
| Project and clock | `projects/{projectId}.eventDate` is read by mobile as a valid Date or missing. `users/{ownerId}.preferences.timezone` is resolved for calendar comparison, with UTC fallback through domain. Upcoming/day/complete normally mean before/same/after the owner's event calendar day. Backend checks use the stored owner's date/timezone, while client screens can temporarily have stale project/preferences. |
| Timeline document | `projects/{projectId}/projectOnlyLists/timeline` contains `config`, `items[]`, and `pendingUpdates[]` defaulting empty. Config extends shared list metadata and specifies literal `type=timeline`, `source` enum default `projectList`, `status:unlocked\|review\|locked\|finalized`, `actionOn:client\|photographer\|none`, `mode:setup\|active\|review`, `finalized:boolean`, `totalEvents:int>=0`, and nullable/optional dates `officialStartTime`, `officialEndTime`, `clientLastViewed`, `clientSubmittedAt`. `config.updatedAt` is the current write/version field. Portal writes clear old top-level `updatedAt` and usually delete the legacy `config.locked`. If canonical status is present it wins over legacy flags in the canonical status helper; the typed mobile schema defaults missing status to unlocked. |
| Event | Unique string `id` and base list item fields incl. string `itemName`, optional item description and base flags; event `type` enum (prep, arrivals, ceremony, portraits, meals, entertainment, other, etc.), optional strings `description` and private `notes`, nullable/optional `startTime` and `endTime` timestamps, optional `duration:int>=0`, optional `locationId` string, author enums `createdBy/updatedBy`, optional notification/weather. Backend rejects a link whose expiry is reached. Projection computes action ownership from canonical status, while reviewer callables also check raw stored `actionOn`. |
| Plan | Mobile plan reads `timeline.enabled/preview/manualAdd/interactive/dynamic/portalSync/maxEvents`. The header specifically applies `preview`, `interactive`, `dynamic`, and quota. Portal uses client-portal access and `portalTimeline.enabled/clientCanAdd/maxEvents`, and enforces both client section and project-list growth limits; domain default for absent portal limit is 10. ## Findings and smallest implementation

1. **The client-turn guard currently protects Add only.** The screenshot's overflow exposes Finalise, Use template and Clear while the client is planning. Reorder and detail writes share the gap. Current Functions approval rejects client-owned and non-`locked` data. General writes also reject the live-client turn. Reuse the existing domain ownership helper in the Timeline composition path for advertised mutations and their handlers. Keep preview and navigation available. [Client-turn checks](C:/eye-doo-monorepo/apps/mobile/src/hooks/use-timeline-screen.ts:66) · [Review guard](C:/eye-doo-monorepo/apps/functions/portal/section/sectionCallables.ts:49)
2. **Unlock has two meanings.** Menu Unlock on a shared active project writes canonical unlocked, which the portal projects as the client's turn, without the hand-back note or clear-revision behavior. It preserves raw owner, despite projection deriving owner from status. This disagrees with “Unlocking allows edits, reordering, and event changes again.” Confirm whether the intended action should reopen for photographer editing or explicitly hand the section back. If it is photographer reopening, reuse the shared existing claim/reopen path for a finalised shared timeline and keep local unlock for an unshared schedule. An already `locked/photographer` review can generally be edited and needs the explicit **Hand back to client** path for revision. Keep Timeline’s current event-day semantics explicit because callable reopening is pre-day only and local unlock currently allows the day. [Unlock service](C:/eye-doo-monorepo/apps/mobile/src/services/base-timeline-service.ts:876) · [Canonical ownership](C:/eye-doo-monorepo/packages/domain/src/portal/section-ownership.ts:15)
3. **The intro and card recognise different finalised signals.** The intro now uses canonical local status, while the summary and mutation lock largely read `config.finalized`. A legacy mismatch or projection lag can pair finalised guidance with Draft or absent Unlock. Likewise “Your client has submitted” can follow a photographer-only claim. In the current hook, an empty finalised list can direct the photographer to a summary menu that is absent. Use the existing normalized status and valid action gates in the composition hook, one factual sentence, and place the eligible next workflow action immediately below it, including the empty case if the same action is permitted.
